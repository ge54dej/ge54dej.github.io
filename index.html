Project 01
DrawBot — SVG Drawing on a Whiteboard

Built a drawing pipeline in RoboDK to render SVG shapes on a whiteboard using a UR10e robotic arm.

Key Points
  • Converted SVG path data into drawing trajectories with pen up/down transitions.
  • Scaled and positioned shapes reliably across the board area.
  • Validated across multiple drawings — spaceship, circle, gear.
Tools
RoboDK UR10e SVG Python
Why the UR10e?

The UR10e was chosen for its 1300 mm reach, which is necessary to cover the full drawing area on a standard whiteboard. While the robot does appear extended in the demo, this was a deliberate configuration choice — the arm is operating within its rated payload and reach envelope. A shorter arm would require repositioning or multiple mounting points, adding complexity. The extended pose was tested for repeatability and remained stable throughout all trials.

SVG to Trajectory Pipeline

SVG files define paths as cubic Bézier curves. The pipeline samples these curves at a fixed resolution into discrete waypoints, then inserts pen-up/pen-down moves between strokes. One of the trickier parts was handling coordinate system transforms — SVG uses a top-left origin with Y going down, while RoboDK uses a right-hand robot frame. Getting the scaling and flipping right across different SVG viewBox values took several iterations.

Lessons Learned

Joint speed limits matter more than expected when drawing fine details — too fast and the arm overshoots corners. Slowing down near sharp path changes improved accuracy significantly. Also, whiteboard marker pressure is surprisingly sensitive: consistent Z-force during contact strokes required careful approach trajectory tuning rather than just position control.

Validation

Three drawings were used as test cases — a spaceship (complex curves), a circle (smooth arc continuity), and a gear (sharp corners + repeated features). This range was deliberate: each stresses a different aspect of the pipeline. The circle checks arc smoothness, the gear checks repeatability and corner handling, and the spaceship tests the full combination.

Project 02
PolishBot — Automated Whiteboard Erasing

Implemented a reliable erase routine using the Franka Panda, teaching a wipe trajectory once and replaying it with ROS 2.

Key Points
  • Recorded a wipe path once, then replayed it to cover a defined erase area.
  • Integrated robot control via a Franka interface using ROS 2.
  • Workflow implemented in Python and C++.
Tools
Franka Panda ROS 2 Python C++
What "Reliably" Actually Means

Reliability here meant the eraser consistently made contact with the board surface across multiple runs without slipping, bouncing, or missing sections. This was achieved by recording the trajectory in Cartesian space (not joint space), so small joint configuration differences on replay don't shift the end-effector path. Cartesian replay keeps the eraser pressed against the board at a consistent angle and force.

Franka + ROS 2 Integration

The Franka Panda communicates with ROS 2 through the franka_ros2 driver. One challenge was latency: the real-time control loop runs at 1 kHz on the robot's internal controller, while ROS 2 topics have variable timing. To avoid jerky motion, trajectory waypoints were pre-loaded and executed via the FCI (Franka Control Interface) directly, with ROS 2 used for monitoring and triggering rather than streaming real-time commands.

Contact Force Handling

A key difficulty with surface wiping is managing contact force. Too little pressure and the eraser doesn't clean; too much and the arm fights against its own stiffness. The Franka's built-in impedance control was used with a tuned stiffness in the Z direction, letting the arm comply slightly to surface irregularities while maintaining steady contact force — without needing an explicit force sensor.

Lessons Learned

Teaching a trajectory "once" sounds simple, but the quality of the recorded path matters enormously. Jerky hand-guidance during recording produces jerky replay. Spending time to record smooth, intentional movements — and trimming start/end artifacts — made a significant difference. I also learned that ROS 2 lifecycle node management is much more robust than simply spinning nodes: it allows graceful startup and shutdown without the robot entering fault states.
